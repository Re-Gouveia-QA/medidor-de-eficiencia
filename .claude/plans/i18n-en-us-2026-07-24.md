Fase 2: resolvido sem o refactor de arquitetura que o plano original cogitava ("schemas viram
funções de locale"). Em vez disso, os schemas em `validators.ts` continuam singletons de módulo,
mas cada `message:` do Zod agora carrega uma *chave* de i18n (ex.: `'validation.emailInvalid'`)

mudança na lib. A tradução de fato acontece em `BaseController.parseOrRedirect`

precisar virar factory por locale.

**Fora do escopo (ainda vale, não faz parte deste plano):**
- Mensagens de `Error` lançadas na camada de Model (ex.: `ActivityModel`/`CategoryModel`) que
  chegam ao controller via `e.message` — continuam pt-BR hardcoded nos models; só o texto de
  fallback do `catch` (quando não é um `Error`) foi traduzido. Mesma classe de problema do Zod
  original, mesmo motivo de adiamento: haveria que tornar esses métodos de Model conscientes de
  locale, o que hoje eles não são.
- Mensagens padrão do próprio Zod para constraints sem `message` customizada (ex.:
  `tempoDesejadoMin`/`valorPadrao`/`duracaoPadraoMin` em `categorySchema`, que usam
  `.int()`/`.positive()` sem string própria) — comportamento pré-existente, não uma regressão
  desta fase; se algum dia ficar visível ao usuário em pt-BR, precisa de mensagem customizada
  antes de poder ser traduzido, o que é escopo novo, não desta fase.

Build/lint verdes; testes 127/130 (mesmas 3 falhas de `GET /` sem Postgres local acessível —
Docker Desktop não estava rodando nesta sessão, ambiente, não regressão).

Fase 3: `formatNumber` (`utils/format.ts`), `formatTimeInZone` e `formatDateShortInZone`
(`utils/time.ts`) passam a receber `Locale` (default `DEFAULT_LOCALE`, mesmo padrão de
`timeZone: string = DEFAULT_TIMEZONE` já usado nessas funções) em vez de `'pt-BR'` fixo nas
chamadas ao `Intl`. Os três controllers que os usam (Activity/Category/Report) passam a envolver
essas funções numa arrow function fechando sobre `req.userLocale`, mesmo padrão já usado pra
`formatTime`/`req.userTimezone`. Confirmado com um script ad-hoc (`Intl` puro, sem rodar o app)
que `formatNumber` diverge por locale como esperado (`1.234,50` pt-BR vs `1,234.50` en-US) e que
`formatDateShortInZone` reordena dd/MM → MM/dd em en-US (comportamento correto de i18n, não um
bug); `formatTimeInZone` continua produzindo o mesmo texto (`HH:mm`) nos dois locales porque
`hourCycle: 'h23'` é fixo independente do locale — importante porque esse mesmo texto alimenta o
`value` de `<input type="time">` em `activities/create.ejs`, que exige HH:mm; mudar pra 12h/AM-PM
em en-US quebraria esse input, então essa parte foi deliberadamente mantida fixa. Chamadas
pré-existentes sem o novo parâmetro (`tests/time.test.ts`) continuam válidas pelo default.

## Goal

Suportar inglês (en-US) como idioma alternativo da interface, sem quebrar o pt-BR atual (idioma
padrão do produto). Fecha o último item pendente e concreto da Fase 6 (o outro item —
reconstruir `medidor_eficiencia.md` — só entra em escopo se for pedido explicitamente).

## Por que isso é "rewrite-shaped" e não uma simples adição

Praticamente toda view EJS tem texto pt-BR hardcoded, todo `req.flash(...)` nos controllers tem
mensagem pt-BR hardcoded, e `src/utils/validators.ts` tem mensagens de erro do Zod hardcoded em
pt-BR nos próprios schemas (definidos uma vez no import do módulo, não por requisição). Isso
excede o gate de "adição" (>5 arquivos / >150 LOC) por uma larga margem e o pedaço dos
validadores Zod é uma decisão de arquitetura real (schemas são singletons a nível de módulo; erro
de validação precisa ser traduzível por requisição). Por isso: Fase 0 primeiro, sem tocar em
validadores ainda, pra validar o mecanismo base antes de decidir como resolver esse pedaço mais
difícil.

## Decisões (minhas, revisáveis — não são o núcleo do problema)

- **Sem lib nova (i18next etc.):** dicionário JSON por idioma + função `t(key, vars?)` com
  fallback pra própria key se a tradução faltar. Combina com "sem build step de front-end" do
  projeto e evita puxar uma dependência pesada pra um problema que um dicionário simples resolve.
- **Detecção/armazenamento do idioma:** cookie `locale` (`pt-BR` padrão), não-`httpOnly`, mesmo
  padrão já usado por `theme` e `tz` (`readThemeCookie`/`readTimezoneCookie` em `app.ts`) — reuso
  direto de um mecanismo já documentado no CLAUDE.md, não uma abordagem nova.
- **Troca de idioma:** botão de texto (ex. "EN"/"PT") no topbar, ao lado do toggle de tema —
  mesmo padrão de interação, sem inventar ícone novo pro catálogo de `icon.ejs`.

## Fora do escopo (por enquanto)

- Traduzir mensagens de validação do Zod (`src/utils/validators.ts`) — resolvido só depois que a
  Fase 0 confirmar o mecanismo base; é o ponto mais arriscado do escopo total.
- Traduzir e-mails transacionais (`EmailService`).
- Qualquer UI de seleção de idioma além do toggle simples (sem dropdown de N idiomas).

## Fase 0 — Protótipo (gate obrigatório antes do rollout completo)

**Objetivo:** provar o mecanismo (dicionário + cookie + toggle) numa página sem formulário/
validação (home), pra isolar a parte fácil da parte difícil (Zod) antes de comprometer o resto do
app.

**Steps:**
1. `src/i18n/index.ts` — tipo `Locale = 'pt-BR' | 'en-US'`, `createTranslator(locale)`.
2. `src/i18n/pt-BR.json` / `src/i18n/en-US.json` — chaves da home + topbar/layout.
3. `src/config/locale.ts` (ou função em `app.ts`, mesmo arquivo de `readThemeCookie`) —
   `readLocaleCookie(req)`.
4. Middleware em `app.ts`: `res.locals.t`/`res.locals.locale` disponíveis em toda view sem cada
   controller precisar passar manualmente (mesmo espírito de `req.userTimezone`).
5. `src/types/express.d.ts` — `userLocale` na `Request` (mesmo padrão de `userTimezone`).
6. `layouts/main.ejs` — `<html lang="...">` dinâmico + botão de troca de idioma.
7. `public/js/locale-toggle.js` — mesmo padrão de `theme-toggle.js` (seta cookie, recarrega).
8. `src/views/home/index.ejs` + `HomeController.ts` — usar `t()` nos textos estáticos; a saudação
   com data (`toLocaleDateString('pt-BR', ...)`) passa a usar `req.userLocale`.

**Files Touched:** `src/i18n/index.ts`, `src/i18n/pt-BR.json`, `src/i18n/en-US.json`,
`src/config/locale.ts`, `src/app.ts`, `src/types/express.d.ts`, `src/views/layouts/main.ejs`,
`public/js/locale-toggle.js`, `src/views/home/index.ejs`, `src/controllers/HomeController.ts`,
mais testes (`tests/i18n.test.ts`, extensão de `tests/routes/auth.routes.test.ts` ou novo teste de
rota pra home).
**Verify:** `npm run build && npm test && npm run lint`; checagem visual manual de `/` nos dois
idiomas (pendente — mesma limitação de Postgres/Docker local já registrada no plano do gráfico de
linha).
**Done When:** troca de idioma na home funciona ponta a ponta (cookie → `<html lang>` →
textos traduzidos → saudação com data no idioma certo), suíte verde.

**Replanning triggers:**
- Se o mecanismo básico (dicionário + cookie + middleware) exigir mais de ~2 ajustes estruturais
  pra funcionar na home, é sinal de que a abordagem "sem lib" não está encaixando bem — reavaliar
  antes de propagar pro resto do app.
